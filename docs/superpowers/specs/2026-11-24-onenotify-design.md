# onenotify — дизайн

Дата: 2026-11-24. Статус: на согласовании. Проверен ревьюером.

Пометка **[моё решение]** — выбор сделан автором документа, а не заказчиком;
его можно менять без пересмотра остального.

Образец для всего, что здесь не описано явно, — репозиторий
`github.com/alekzonder/onecheck` (рядом: `../onecheck`). Там, где сказано
«как в onecheck», исполнитель читает соответствующий код и документацию
onecheck и повторяет поведение.

## 1. Зачем

`onecheck` проверяет сервер и пишет в каталог-очередь событие на каждый
подтверждённый переход «упало» / «восстановилось». Сам он никого не
уведомляет. `onenotify` — отдельная утилита, которая забирает эти события и
рассылает уведомления в каналы: Telegram, почта, ntfy. Кроме событий onecheck,
она отправляет произвольное сообщение из командной строки (`onenotify send`),
чтобы ею могли пользоваться другие скрипты.

Устроена так же, как onecheck: ядро и модули-провайдеры как отдельные
исполняемые файлы с версионированным JSON-протоколом, запуск из cron или
systemd timer, тот же способ сборки, установки, релиза и документирования.

## 2. Цели, не-цели, анти-цели

Цели:

- Один бинарник `onenotify` + модули доставки `onenotify-<name>`, которые
  подхватываются из каталога модулей без пересборки.
- Единый вид уведомления для всех каналов: ядро формирует `title` и `text`,
  модуль только доставляет.
- Каждое уведомление содержит имя хоста.
- Надёжная доставка в несколько каналов: недоступный канал не задерживает
  остальные и не вызывает повторов в них; недоставленное повторяется до
  истечения срока.
- `onenotify send` — отправка своего сообщения (`title`, `text` аргументом, из
  файла или stdin).
- Установка и обновление модулей и самого `onenotify` из GitHub Releases,
  `install.sh`, `make build` / `make check`, сайт документации — как в onecheck.
- Бандл-модули первой версии: `telegram`, `mail`, `ntfy`.

Не-цели (в этой версии не делаем):

- Режим сервиса и HTTP API на localhost. Решено заказчиком: позже.
- Шаблоны сообщений. Решено заказчиком: формат фиксированный, шаблоны — если
  потребуется.
- Маршрутизация: фильтры по тегам, конфигу, типу перехода. Каждое событие
  уходит во все включённые каналы. **[моё решение]**
- Повторные напоминания «всё ещё лежит», группировка и подавление шквала
  событий.
- Команда возврата сообщений из `failed` в очередь. Файл можно перенести
  руками, пока не истёк его срок.
- Разделение привилегий с onecheck: `onenotify` запускается тем же
  пользователем, что и onecheck (обычно root), см. §13. **[моё решение]**
- Приём сообщений от непривилегированных скриптов через общий каталог-входящие.
  Задел есть (источники в конфиге типизированы, §6), сам тип не делаем.
  **[моё решение]**
- Вложения, HTML-письма, кнопки, форматирование текста пользователем.
- Windows. Платформы как в onecheck: linux/amd64, linux/arm64; darwin
  собирается для разработки.

Анти-цели (провал, даже если «работает»):

- Потерянное уведомление: событие, забранное из очереди onecheck, должно быть
  либо доставлено, либо лежать в очереди канала, либо лежать в `failed` с
  записью в логе. Молча исчезнуть оно не может.
- Секрет канала (токен, пароль) в логе, в выводе команд или в файлах очереди.
- Один лежащий канал, из-за которого остальные получают одно и то же
  уведомление повторно.
- Модуль, который сам решает, что и кому отправлять.

## 3. Рассмотренные подходы

**Отдельный инструмент или часть onecheck**

1. **Отдельный инструмент `onenotify` — выбрано заказчиком.** Разный жизненный
   цикл (короткая проверка против ретраев и сетевых ошибок), отказ канала не
   ломает проверки, секреты каналов не нужны onecheck, польза вне onecheck.
   Цена: копия инфраструктурного кода и второй конфиг.
2. Всё внутри onecheck. Отклонено: зависшая отправка либо задерживает
   проверки, либо требует очереди повторов внутри onecheck.

**Как хранить недоставленное при нескольких каналах**

1. **Раскладка по каналам — выбрано заказчиком.** При заборе события ядро
   пишет готовое сообщение в `spool/<канал>/<id>.json` для каждого канала и
   удаляет исходный файл; доставил — удалил файл канала. Один файл — одна
   доставка, сообщения не переписываются, каналы независимы. Цена: копия
   сообщения на канал.
2. Один файл на событие с отметками «канал — доставлено». Отклонено:
   изменяемое состояние, дубль при сбое между отправкой и записью отметки.
3. Без своего каталога: удалять событие из очереди onecheck, когда все каналы
   ответили успехом. Отклонено: при одном лежащем канале остальные получают
   повтор на каждом запуске.

**Кто формирует текст**

1. **Ядро формирует `title` и `text` по фиксированным правилам, модуль решает
   только, как их показать в своём канале — выбрано заказчиком.**
2. Шаблоны в конфиге. Отложено заказчиком.
3. Модуль получает сырое событие и сам строит текст. Отклонено: уведомления
   разных каналов разойдутся, сторонний модуль обязан знать формат onecheck.

**Как показать параметры правила, не раскрыв секреты**

1. **onecheck пишет в событие параметры так, как они записаны в конфиге, до
   подстановки `${VAR}`; правило может отключить это ключом `event_params:
   false` — выбрано заказчиком.** Отдельный документ:
   `../onecheck/docs/superpowers/specs/2026-11-24-event-params-design.md`.
2. Пометка секретных полей в схеме модуля. Отклонено: не покрывает
   произвольные заголовки, `argv`, тело запроса.

**Общий код с onecheck**

1. **Копия нужных пакетов onecheck с адаптацией. [моё решение]** Репозитории
   независимы, релизы не связаны.
2. Общая публичная библиотека или один репозиторий на оба инструмента.
   Отклонено: связывает релизы и требует сначала переделать onecheck.

## 4. Обзор архитектуры

```
cron/systemd ─▶ onenotify run
                  │ 1. читает конфиг + include, берёт блокировку
                  │ 2. забор: для каждого события из источников
                  │      событие → сообщение (title, text, level, host)
                  │      пишет spool/<канал>/<id>.json для каждого канала
                  │      удаляет исходный файл
                  │ 3. доставка: каналы параллельно, внутри канала по порядку
                  │      onenotify-<module> send
                  │      stdin: params канала + сообщение   stdout: итог
                  │      доставлено → файл удалён
                  │      временная ошибка → канал ждёт следующего запуска
                  │      постоянная ошибка или истёк срок → failed/<канал>/
                  │ 4. печатает итог, exit-code
                  ▼
   spool/<канал>/<id>.json   failed/<канал>/<id>.json   log

onenotify send ─▶ пишет сообщение в spool/<канал>/ и запускает доставку
```

Принцип: **ядро решает, что, кому и каким текстом отправить; модуль только
доставляет.** В модуле нет чтения очередей, повторов и выбора получателей
сверх своих `params`.

Go-модуль `github.com/alekzonder/onenotify`, версия Go и библиотеки — те же,
что в onecheck (`cobra`, `yaml.v3`, `santhosh-tekuri/jsonschema`, `log/slog`).
Раскладка пакетов — на усмотрение исполнителя, с такими границами:

- `cmd/onenotify` — CLI ядра.
- `cmd/onenotify-telegram`, `cmd/onenotify-mail`, `cmd/onenotify-ntfy` —
  модули.
- `pkg/module` — публичный SDK модуля: типы протокола и `module.Main`.
- внутренние пакеты: конфиг; источники (разбор события onecheck); построение
  сообщения; очередь (spool, failed, блокировка, атомарная запись); запуск
  модулей; доставка; вывод; менеджер модулей (GitHub); ротация; логирование.

Из onecheck копируются с переименованием и адаптацией: поиск и запуск модулей
(`internal/modules`), GitHub-клиент и установка (`internal/github`,
`internal/install`), логирование и ротация логов (`internal/logging`,
`internal/rotate`), единицы размера и времени (`internal/units`), атомарная
запись и блокировка (`internal/store`), загрузка конфига с include и `${VAR}`
(`internal/config`), команды `paths`, `module`, `self-update`, `logrotate`,
`version`, сборка тестовых модулей (`internal/testmods`), тест установщика
(`internal/installsh`).

## 5. CLI

```
onenotify [run]            забрать события и доставить очереди (по умолчанию)
onenotify send             поставить в очередь своё сообщение и доставить
onenotify validate         проверить конфиг и каналы, ничего не отправляя
onenotify status           очереди и состояние каналов
onenotify paths            пути всего, что читает и пишет onenotify
onenotify module list|search|install|update|remove      как в onecheck
onenotify self-update [--version X]
onenotify logrotate [--logs] [--failed]   без флагов — и то, и другое
onenotify version
```

Глобальные флаги: `-c, --config <path>`, `--log-level debug|info|warn|error`.

Поиск конфига, по очереди: `--config` → `$ONENOTIFY_CONFIG` →
`/etc/onenotify/config.yaml` → `$HOME/.config/onenotify/config.yaml`.

### `run`

Флаги: `-o, --output text|json`, `--channel <name>` (повторяемый: доставлять
только в эти каналы; забор событий при этом выполняется как обычно, для всех
каналов).

Вывод `text`, по строке на попытку доставки и итог:

```
SENT    ops-telegram  20261123T100200Z-main-api-health-fail  (telegram, 312ms)
WAIT    admin-mail    20261123T100200Z-main-api-health-fail  (mail, 10s)
        dial tcp 10.0.0.5:587: connection refused
FAILED  phone         20261123T090000Z-send-4f2a9c1e  (ntfy)
        expired at 2026-11-24T09:00:00Z

3 messages: 1 sent, 1 waiting, 1 failed
```

Когда делать было нечего, печатается только итоговая строка
`0 messages`. Формат `json` — объект с массивом тех же записей и счётчиками;
точные имена полей — на усмотрение исполнителя, с документацией.

Exit-коды:

| Код | Смысл |
|---|---|
| 0 | всё, что было в очередях, доставлено; или очереди пусты |
| 1 | что-то осталось ждать или ушло в `failed` |
| 2 | `onenotify` не смог отработать: конфиг, блокировка, запись файлов |

Если блокировку держит другой запуск — код `2` и сообщение, как в onecheck.

### `send`

```
onenotify send --title "backup finished" --text "42 GB in 13m"
onenotify send --title "backup failed" --text-file /tmp/backup.log --level error
pg_dump ... 2>&1 | onenotify send --title "pg_dump output" --text-file -
```

Флаги:

- `--title <text>` — обязателен;
- `--text <text>` или `--text-file <path>` (`-` — stdin); оба не заданы —
  сообщение без текста; заданы оба — ошибка;
- `--level info|ok|warning|error` (по умолчанию `info`);
- `--tag <tag>` (повторяемый);
- `--channel <name>` (повторяемый; без него — все включённые каналы);
- `--queue-only` — только поставить в очередь, не доставлять.

К заголовку ядро добавляет префикс `[<host>] `, как для событий.

Что делает: пишет сообщение в `spool/<канал>/` выбранных каналов (блокировка
для этого не нужна), затем берёт блокировку и выполняет то же, что
`run --channel <выбранные>`: забор из источников и доставку очередей этих
каналов — всей очереди, чтобы сохранить порядок. Забор нужен, чтобы `send` и
`run` вели себя одинаково после сбоя (см. §8). Если блокировка
занята, ждёт её до 10 секунд; не дождался — сообщение остаётся в очереди и
уйдёт со следующим запуском `run`. **[моё решение]**

Вывод — как у `run`. Exit-коды: `0` — сообщение доставлено во все выбранные
каналы; `1` — поставлено в очередь, но хотя бы в один канал не доставлено
(или `--queue-only` не использовался и блокировка не получена); `2` — ошибка:
нет такого канала, нет включённых каналов, не удалось записать в очередь. С
`--queue-only` код `0` означает «поставлено в очередь».

Текст из файла или stdin читается не более чем на `limits.text` (§6) плюс один
байт; если больше — обрезается до лимита с пометкой в конце
`\n… (truncated)`.

### `validate`

Проверяет: конфиг (неизвестные ключи — ошибка), наличие и совместимость модуля
каждого канала, `params` канала по `params_schema` модуля, существование
каталогов источников (отсутствующий — предупреждение, не ошибка: onecheck мог
ещё не запускаться). Ничего не отправляет. Нет ни одного включённого канала —
предупреждение. Exit-коды `0` / `2`.

Проверить сам канал (токен, адрес) — `onenotify send --title test --channel
<name>`.

### `status`

```
$ onenotify status
CHANNEL       MODULE    QUEUED  OLDEST               STATE
ops-telegram  telegram  0       -                    ok
admin-mail    mail      3       2026-11-23 10:02 UTC failing since 2026-11-23 10:03 UTC: connection refused
phone         ntfy      0       -                    disabled

failed: 2 messages in /var/lib/onenotify/failed
sources:
  onecheck  /var/lib/onecheck/events  1 waiting
```

`--json` — то же для скриптов. Ничего не меняет, блокировку не берёт.
Очереди каналов, которых нет в конфиге, показываются со `STATE` `not in
config`.

### `paths`

Как `onecheck paths`: конфиг и как он найден, include-файлы, лог, `spool`,
`failed`, каталоги источников, каталог модулей, бинарник; `(missing)`,
`--json`.

## 6. Конфиг

```yaml
host: web-01                  # имя хоста в уведомлениях; по умолчанию системное

log:
  level: info                 # флаг --log-level важнее
  dir: /var/log/onenotify     # файл: <dir>/onenotify.log
  format: text                # text | json
  rotate:                     # правила для onenotify logrotate
    max_size: 10MB
    keep: 5
    max_age: 30d
    compress: true

paths:
  modules: /usr/lib/onenotify/modules
  spool:   /var/lib/onenotify/spool
  failed:  /var/lib/onenotify/failed

sources:                      # откуда забирать события
  - type: onecheck            # единственный тип в этой версии
    path: /var/lib/onecheck/events

include:                      # ещё файлы с каналами; пути — от каталога конфига
  - conf.d/*.yaml

queue:
  ttl: 24h                    # срок сообщений без собственного срока (send)
  failed_ttl: 7d              # сколько хранить failed; чистит logrotate

limits:
  text: 64KB                  # наибольший text одного сообщения

run:
  parallel: 4                 # каналов, доставляемых одновременно

defaults:                     # для каналов, где не указано
  timeout: 30s

modules:
  repos:                      # где module search ищет по умолчанию
    - alekzonder/onenotify

channels:
  - name: ops-telegram        # уникально, [a-z0-9][a-z0-9_.-]*
    module: telegram
    enabled: true
    timeout: 10s
    params:                   # вход модуля, см. документацию модуля
      token: "${TELEGRAM_TOKEN}"
      chat_id: "-1001234567890"

  - name: admin-mail
    module: mail
    params:
      host: smtp.example.com
      port: 587
      tls: starttls
      username: alerts@example.com
      password: "${SMTP_PASSWORD}"
      from: alerts@example.com
      to: [admin@example.com]

  - name: phone
    module: ntfy
    params:
      url: https://ntfy.sh
      topic: my-server-alerts
      token: "${NTFY_TOKEN}"
```

- Все ключи необязательны; значения выше — умолчания для root. Для остальных
  пользователей пути по той же схеме, что в onecheck
  (`$HOME/.local/state/onenotify/...`, `$HOME/.local/lib/onenotify/modules`).
  Источник по умолчанию один — каталог событий onecheck по умолчанию для того
  же пользователя; ключ `sources: []` отключает забор.
- Имени конфига (`name` в onecheck) нет: один экземпляр — один каталог `spool`.
  Два экземпляра на хосте — разные `paths`. **[моё решение]**
- Неизвестные ключи — ошибка. Размеры и длительности — как в onecheck.
- `${VAR}` подставляется в строках `params` каналов из окружения по правилам
  onecheck (`$${VAR}` — литерал, неопределённая переменная — ошибка). Больше
  нигде подстановки нет.
- Include-файлы содержат только ключ `channels`. Имена каналов уникальны по
  всем файлам.
- `host`: пустая строка недопустима; если системное имя получить не удалось и
  ключ не задан — ошибка конфига.

## 7. Сообщение

Внутреннее представление, оно же содержимое файла очереди и то, что получает
модуль:

| Поле | Описание |
|---|---|
| `id` | уникальный id; начинается с времени UTC `YYYYMMDDTHHMMSSZ`, поэтому лексикографический порядок хронологический |
| `source` | `onecheck` или `send` |
| `host` | имя хоста |
| `level` | `error`, `ok`, `warning`, `info` |
| `title` | одна строка, уже с префиксом `[<host>] ` |
| `text` | многострочный простой текст, может быть пустым |
| `tags` | список строк, может быть пустым |
| `created_at` | когда произошло (UTC, RFC 3339): `at` события или время вызова `send` |
| `expires_at` | после этого момента доставка не выполняется |

`id` для события onecheck — `id` события. Для `send` —
`<время UTC>-send-<8 hex случайных символов>`.

`expires_at` для события onecheck — `expires_at` события; если его нет —
`created_at` + `queue.ttl`. Для `send` — время вызова + `queue.ttl`.

### Сообщение из события onecheck

`level`: `fail` → `error`, `recovered` → `ok`, иное значение `transition` →
`info`.

`title`: `[<host>] FAIL <config>/<rule>` или
`[<host>] RECOVERED <config>/<rule>`; для неизвестного перехода — значение
`transition` в верхнем регистре на месте слова.

`tags` — `result.tags`.

`text` — строки в таком порядке; строка опускается, если данных нет:

```
module: http
url: https://example.com/health
headers.Authorization: Bearer ${API_TOKEN}
tags: api, web
at: 2026-11-23 10:02:00 UTC
failed 3 runs in a row:
- status: expected equals 200, got 503
```

1. `module: <result.module>`.
2. Параметры правила из поля `params` события (появится в onecheck отдельным
   изменением; в событиях без него эти строки пропускаются). По одной строке
   `ключ: значение`, ключи отсортированы. Вложенные объекты разворачиваются в
   `a.b.c`; массивы скаляров и всё остальное печатается компактным JSON в одну
   строку. Значение длиннее 200 символов обрезается с `…`; не более 20 строк,
   дальше строка `… and N more params`.
3. `tags: a, b` — если есть.
4. `at: <время события> UTC` в виде `YYYY-MM-DD HH:MM:SS UTC`.
5. Только для `fail`:
   - если `result.status` — `error`: строка `error: <result.error>`;
   - иначе строка `failed <consecutive> runs in a row:` (при `consecutive` = 1 —
     `failed:`) и по строке `- <message>` на каждый элемент `result.failures`;
     не более 10, дальше `… and N more`.

   Текст ошибки и каждое сообщение условия отправляются как есть, но
   обрезаются до 300 символов с `…`; переводы строк внутри заменяются
   пробелами. Решено заказчиком.

Для `recovered` пункт 5 отсутствует: только имя, параметры, теги и время —
так решено заказчиком.

Поле `result.output` (тело ответа, stdout) в уведомление не включается. Но
сообщение условия содержит фактическое значение (`... got <значение>`), и для
условия на `body` или `stdout` это фрагмент ответа или вывода — до 300
символов он в уведомление попадёт.

**Скрытое правило.** Если в событии `"redacted": true` (правило onecheck с
`event_params: false`), пункты 2 и 5 опускаются целиком: в уведомлении
остаются имя правила в заголовке, модуль, теги и время. Решено заказчиком.
Событие без ключа `redacted` (старый onecheck) считается нескрытым.

Время всегда в UTC. **[моё решение]** Тексты строк английские, как весь вывод
onecheck. **[моё решение]**

Разбор события терпим к неизвестным полям. Файл, который не разбирается как
событие (не JSON, нет `id`, `rule` или `transition`), переносится в
`failed/_unreadable/<имя файла>` с предупреждением и из источника удаляется.

## 8. Очередь, доставка, блокировка

### Каталоги

```
<paths.spool>/.lock                    блокировка запуска
<paths.spool>/.owner                   какой конфиг владеет каталогом, как в onecheck
<paths.spool>/<канал>/<id>.json        сообщение, ждущее доставки
<paths.spool>/<канал>/.status.json     состояние канала (см. ниже)
<paths.failed>/<канал>/<id>.json       недоставленное: срок или постоянная ошибка
<paths.failed>/_unreadable/<файл>      нечитаемые файлы из источников
```

Файл очереди — сообщение из §7 плюс служебное поле `version: 1`. Файл в
`failed` — то же плюс `failed_at` и `reason` (текст последней ошибки или
`expired`). Параметров канала и секретов в этих файлах нет.

Права как в onecheck: каталоги `0750`, файлы `0640`. Все файлы пишутся
атомарно (временный файл с именем на `.` в том же каталоге, затем rename).
Имена файлов из id — через ту же функцию обезвреживания, что в onecheck.

### Блокировка

`flock` (исключающая, без ожидания) на `<paths.spool>/.lock` на весь запуск
`run`: и забор, и доставка. Второй `run` сразу завершается с кодом `2`.
`.owner` — как в onecheck: другой файл конфига с тем же `paths.spool`
отклоняется.

Под блокировкой выполняются: забор из источников, доставка, перенос в
`failed`, запись `.status.json`, `logrotate --logs` (если блокировка занята —
ротация логов пропускается с сообщением, как в onecheck).

Без блокировки: запись нового сообщения в очередь командой `send` (атомарный
rename; читающий запуск игнорирует имена на `.`), `status`, `paths`,
`validate`, `logrotate --failed`.

### Забор

Для каждого источника: список `*.json` без имён на `.`, по возрастанию имени.
Для каждого файла:

1. разобрать, построить сообщение;
2. записать его в `spool/<канал>/<id>.json` для каждого включённого канала;
3. удалить исходный файл.

Перед удалением исходного файла (шаг 3) записанные файлы и их каталоги
сбрасываются на диск (`fsync` файла до rename и каталога после): иначе при
отключении питания удаление может сохраниться, а новые файлы — нет, и
уведомление пропадёт. Этим запись очереди отличается от `WriteFileAtomic` в
onecheck.

Если шаг 2 не удался хотя бы для одного канала (диск полон, нет прав), это
сбой собственных файлов onenotify, а не канала: исходный файл остаётся, забор
прекращается, **доставка в этом запуске не выполняется ни для одного канала**,
код выхода `2`. Иначе канал, в который запись удалась, получал бы то же
уведомление на каждом запуске. Следующий запуск повторит забор: запись того же
id перезаписывает тот же файл.

Доставка начинается только после успешного завершения забора, и любая команда,
которая доставляет (`run`, `send`), сначала выполняет забор. Поэтому сбой
между шагами 2 и 3 дублей не даёт: следующий запуск сначала перезапишет те же
файлы и удалит источник, и только потом начнёт доставку.

Если включённых каналов нет, забор не выполняется: события остаются в очереди
onecheck (и удаляются его `logrotate` по сроку), в лог — предупреждение.

Событие, срок которого уже истёк на момент забора, обрабатывается как обычно
и уйдёт в `failed` на этапе доставки.

### Доставка

Каналы обрабатываются параллельно (`run.parallel`), сообщения одного канала —
строго по порядку имён файлов, по одному. Для каждого сообщения:

1. `expires_at` прошёл → в `failed` с причиной `expired`, предупреждение.
2. Запуск `onenotify-<module> send` (§9) с таймаутом канала.
3. Итог:
   - **доставлено** → файл удалён;
   - **постоянная ошибка** (это сообщение этим каналом доставить нельзя) → в
     `failed`, предупреждение, переход к следующему сообщению;
   - **временная ошибка** (сеть, таймаут, отказ авторизации, лимит запросов,
     сбой самого модуля) → сообщение остаётся, **обработка этого канала в этом
     запуске прекращается**. Так сохраняется порядок («упало» раньше
     «восстановилось») и недоступный канал не тратит по таймауту на каждое
     сообщение очереди.

Файл в очереди канала, который не читается как сообщение, переносится в
`failed/<канал>/` как есть, с предупреждением; обработка канала продолжается.

Канал отключён (`enabled: false`), отсутствует в конфиге, его модуль не
установлен или несовместим: доставка не выполняется, сообщения ждут и уходят в
`failed` по сроку. Проверка срока (шаг 1) выполняется на каждом запуске для
всех подкаталогов `spool`, включая каналы, которых нет в конфиге.

Гарантия — at-least-once на канал: если модуль отправил, а ядро не успело
удалить файл (сбой, kill), сообщение уйдёт повторно.

### Состояние канала

`.status.json` в каталоге канала:

```json
{
  "failing_since": "2026-11-23T10:03:00Z",
  "consecutive": 14,
  "last_error": "dial tcp 10.0.0.5:587: connection refused",
  "retry_at": "2026-11-23T10:17:30Z"
}
```

- Пишется при временной ошибке; удаляется при первой успешной доставке.
- `retry_at` — если модуль вернул `retry_after_ms`: до этого момента канал
  пропускается.
- Нужен, чтобы не писать одно и то же предупреждение на каждом запуске:
  первая временная ошибка канала логируется как `warn` (и попадает в stderr,
  cron пришлёт письмо), повторные — как `info`; восстановление канала — `info`.
- Потеря или порча файла безопасна: канал считается исправным.

### `logrotate`

Логи — как в onecheck. `--failed`: удаляет из `paths.failed` файлы старше
`queue.failed_ttl` (по `failed_at`, для нечитаемых — по времени изменения), а
из `paths.spool` — оставшиеся временные файлы старше `queue.ttl`.

## 9. Протокол модулей

Версия протокола **1**. Правила те же, что в onecheck: модуль — исполняемый
файл `onenotify-<name>` в каталоге модулей (в `PATH` не ищется); stdout только
для ответа, диагностика в stderr (попадает в лог на уровне `debug`); код
выхода `0`, если ответ выдан, включая ответ с ошибкой; модуль запускается в
своей группе процессов и убивается вместе с ней по таймауту; состояния между
запусками нет; добавление необязательных ключей версию не меняет, неизвестные
ключи обе стороны игнорируют.

### `onenotify-<name> describe`

```json
{
  "protocol": 1,
  "name": "telegram",
  "version": "0.1.0",
  "description": "Send a message to a Telegram chat through the Bot API",
  "params_schema": { "type": "object", "additionalProperties": false, "...": "..." }
}
```

`protocol`, `name`, `version` обязательны; `name` равен имени в файле.
`params_schema` — JSON Schema (draft 2020-12) для `params` канала; ядро
проверяет ею `params` в `validate` и перед отправкой.

### `onenotify-<name> send`

Запрос на stdin:

```json
{
  "protocol": 1,
  "channel": "ops-telegram",
  "params": { "token": "123:abc", "chat_id": "-1001234567890" },
  "message": {
    "id": "20261123T100200Z-main-api-health-fail",
    "source": "onecheck",
    "host": "web-01",
    "level": "error",
    "title": "[web-01] FAIL main/api-health",
    "text": "module: http\nurl: https://example.com/health\n...",
    "tags": ["api"],
    "created_at": "2026-11-23T10:02:00Z"
  },
  "timeout_ms": 10000
}
```

`params` — после подстановки `${VAR}` и проверки схемой.

Ответ на stdout:

```json
{ "delivered": true, "error": null }
```

```json
{
  "delivered": false,
  "error": { "message": "429 Too Many Requests", "permanent": false, "retry_after_ms": 30000 }
}
```

| Ключ | Описание |
|---|---|
| `delivered` | `true` — провайдер принял сообщение |
| `error.message` | что пошло не так; без секретов |
| `error.permanent` | `true` — именно это сообщение этим каналом доставить нельзя, повтор не поможет. По умолчанию `false` |
| `error.retry_after_ms` | необязательно: не обращаться к каналу раньше этого времени |

Правило для авторов модулей: `permanent` — только когда провайдер отверг
содержимое именно этого сообщения. Неверный токен, неизвестный получатель,
отказ по политике сервера, недоступный сервер, лимит — временные ошибки:
администратор исправит конфиг, и сообщение уйдёт. При сомнении ошибка
временная: постоянная ошибка переходит к следующему сообщению, и ошибочная
классификация опустошила бы всю очередь в `failed` из-за опечатки в конфиге.
Сообщение, которое не удаётся доставить из-за временной ошибки, всё равно
уйдёт в `failed` по сроку.

Ненулевой код выхода, некорректный JSON, пустой вывод, таймаут — ядро считает
временной ошибкой с соответствующим текстом.

Модуль сам приводит сообщение к ограничениям своего канала: обрезает слишком
длинный текст (с `…` в конце), экранирует разметку, выбирает оформление по
`level`. Сообщение никогда не отвергается из-за длины.

### SDK

`pkg/module`: типы протокола, `module.Main(module.Module{Description, Send})`,
где `Send(ctx, req) error`; `module.DecodeParams` (строгий разбор);
`module.Permanent(err)` и `module.RetryAfter(err, d)` для классификации
ошибок. `Main` обрабатывает `describe` и `send`, применяет `timeout_ms` к
контексту, превращает возвращённую ошибку в ответ.

## 10. Бандл-модули

Общее: каждый принимает необязательный параметр с адресом сервера, которым в
тестах подставляется локальный сервер. Оформление по `level` — **[моё
решение]** во всех трёх.

### telegram

`params`: `token` (обяз.), `chat_id` (обяз., строка или число),
`message_thread_id`, `silent_ok` (bool; `true` — сообщения уровня `ok`
отправляются без звука; по умолчанию `false`, то есть со звуком), `api_url` (по умолчанию `https://api.telegram.org`).

Bot API `sendMessage`, `parse_mode: HTML`: `<b>заголовок</b>`, пустая строка,
текст; и заголовок, и текст экранируются. Перед заголовком значок по уровню:
`error` 🔴, `ok` 🟢, `warning` 🟡, `info` ℹ️. Лимит 4096 символов: текст
обрезается.

Ошибки: `429` → временная с `retry_after_ms` из `parameters.retry_after`.
Постоянные — только `400` с описанием, говорящим о содержимом: `message is too
long`, `can't parse entities`, `message text is empty`. Любой другой ответ, в
том числе остальные `400` (`chat not found`, `message thread not found`,
переезд группы в супергруппу), `401`, `403`, `404`, `5xx`, сеть → временные. Токен не должен попадать в текст ошибки
(он входит в URL запроса — вырезать).

### ntfy

`params`: `url` (по умолчанию `https://ntfy.sh`), `topic` (обяз.), `token`
либо `username` + `password`, `priority` (необязательное переопределение).

Публикация JSON-запросом на корневой URL (`topic`, `title`, `message`,
`priority`, `tags`), чтобы не кодировать не-ASCII в заголовках. Приоритет по
уровню: `error` 4, `warning` 3, `ok` 3, `info` 2. Теги ntfy по уровню:
`rotating_light`, `warning`, `white_check_mark`, `information_source`; теги
сообщения добавляются следом. Лимит тела 4096 байт: текст обрезается по
границе символа.

Ошибки: `429` → временная (с `Retry-After`, если есть); `413` → постоянная;
всё остальное, включая `400`, `401`, `403`, `404`, `5xx`, сеть → временные.

### mail

`params`: `host` (обяз.), `port` (по умолчанию по `tls`: 587 / 465 / 25),
`tls` (`starttls` по умолчанию | `tls` | `none`), `username`, `password`,
`from` (обяз.), `to` (обяз., непустой список), `helo` (по умолчанию имя хоста).

SMTP стандартной библиотекой. Письмо `text/plain; charset=utf-8`: тема —
`title` (RFC 2047 при не-ASCII), тело — `text`. `Message-ID` строится из `id`
сообщения и домена `from`, `Date` — время отправки. Аутентификация — если
задан `username`. При `starttls` сервер без STARTTLS — ошибка, а не отправка
открытым текстом.

Ошибки: постоянная — только `552` (превышен размер письма). Всё остальное
(сеть, TLS, аутентификация, `4xx`, отказ по адресу отправителя или получателя,
отказ по политике на `DATA`) → временные.

## 11. Логирование

Как в onecheck: файл `<log.dir>/onenotify.log` (без подкаталога имени), `slog`,
уровни, `warn` и выше дублируются в stderr, `--log-level` включает вывод в
stderr на своём уровне, в stdout лог не пишется.

| Уровень | Что пишется |
|---|---|
| `error` | запуск, который не смог завершиться |
| `warn` | первая временная ошибка канала; сообщение ушло в `failed`; нечитаемый файл в источнике; нет включённых каналов |
| `info` | строка на каждое забранное событие и каждую попытку доставки; повторные ошибки канала; восстановление канала; итог запуска |
| `debug` | найденные модули; запросы модулям без `params`; stderr модулей |

`params` каналов не логируются ни на каком уровне. В запросе, который пишется
в лог на `debug`, `params` заменяется на список имён ключей.

**Переменные окружения** управления модулями и self-update — с префиксом

`ONENOTIFY_SELF_UPDATE_TARGET`), `GITHUB_TOKEN` без изменений.

**AGENTS.md.** Копия правил onecheck (сообщения коммитов `chg:` / `fix:` /

лимит сложности, тесты без сети и вне `t.TempDir()`, документация при видимых
изменениях) с картой этого репозитория и правилами дизайна:

- модуль только доставляет; что, кому и каким текстом — решает ядро;
- протокол версионирован, несовместимое изменение — новая версия;
- файлы очереди и `failed` пишутся атомарно;
- уведомление не теряется: исходное событие удаляется только после записи во
  все очереди каналов, файл очереди — только после успешной доставки или
  переноса в `failed`;
- секреты каналов не попадают в логи, вывод и файлы очереди.

**Тесты.**

- Построение сообщения из события — табличные тесты с эталонными `title` и
  `text`: `fail`, `fail` со статусом `error`, `recovered`, без `params`, с
  вложенными и длинными `params`, много ошибок, длинная и многострочная
  ошибка, `redacted: true`, неизвестный переход.
- Очередь: забор пишет во все каналы и удаляет источник; сбой записи оставляет
  источник; повторный забор не даёт дублей; порядок доставки; остановка канала
  на временной ошибке при продолжении остальных; постоянная ошибка и
  истечение срока → `failed`; `retry_at`; нечитаемый файл; блокировка.
- Запуск модулей — на фальшивом модуле из `testdata`, который умеет вести себя
  неправильно (ненулевой код, мусор, зависание), как `fakemod` в onecheck.
- Бандл-модули — против локального сервера в тесте: HTTP для telegram и ntfy,
  SMTP-заглушка для mail; проверяются тело запроса, обрезка, экранирование,
  классификация ошибок, отсутствие токена в тексте ошибки.
- CLI — сквозные тесты с реальными собранными модулями (`internal/testmods`):
  `run`, `send`, `validate`, `status`, `paths`, exit-коды.
- `examples/config.yaml` загружается и проверяется тестом; тест падает, если у
  бандл-модуля нет примера канала.
- Управление модулями и self-update — тесты переносятся вместе с кодом.
- Сеть (кроме loopback) и запись вне `t.TempDir()` в тестах запрещены.

## 13. Права и безопасность

- `onenotify` запускается тем же пользователем, что и onecheck. Каталог
  событий onecheck создаётся с правами `0750`, удалять из него может только
  владелец.
- Конфиг содержит секреты или ссылки на них. Документация рекомендует права
  `0600` и `${VAR}`; где задать переменные для cron и systemd — описывается в
  `getting-started`.
- Модуль выполняется с правами `onenotify` и получает секреты канала;
  устанавливать модули только из доверенных репозиториев. Проверка `sha256`
  по `checksums.txt` — как в onecheck (целостность, не подлинность).
- Текст уведомления уходит третьей стороне (Telegram, ntfy.sh, почтовый
  сервер). В него попадают: параметры правил onecheck в том виде, в каком
  записаны в конфиге onecheck (секреты там должны быть заданы через `${VAR}`),
  и текст ошибки с фактическими значениями, до 300 символов на строку. Для
  правил, где это недопустимо, — `event_params: false` в onecheck: уведомление
  останется без параметров и без текста ошибки. Это описывается в
  документации (`messages`).

## 14. Порядок работ

1. Изменение onecheck: поля `params` и `redacted` в событии, ключ
   `event_params`, URL без секретов в ошибке модуля `http` (отдельный
   документ, отдельный план). `onenotify` от него не зависит: события без
   этих полей обрабатываются.
2. `onenotify`: каркас и инфраструктура, перенесённая из onecheck; затем
   сообщение и очередь; затем протокол, SDK и три модуля; затем `send`,
   `status`; затем установщик, CI, документация.

## 15. Что остаётся исполнителю

- Раскладка внутренних пакетов и имена типов.
- Точный формат JSON-вывода `run`, `send`, `status`, `paths`.
- Тексты `--help` и сообщений об ошибках (по образцу onecheck).
- Детали реализации SMTP-заглушки и фальшивого модуля в тестах.
- Точные тексты сообщений провайдерам в пределах описанного в §10.
